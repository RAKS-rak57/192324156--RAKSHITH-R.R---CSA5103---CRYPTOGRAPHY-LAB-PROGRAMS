1.1 The Privacy & Cryptographic Dilemma

Digital images generated by contemporary smartphones and digital SLR cameras contain an invisible layer of surveillance metadata governed by the Exchangeable Image File Format (EXIF) standard. Stored within binary application markers (specifically APP1 marker 0xFFE1), EXIF blocks bundle high-risk personally identifiable telemetry:

  • Geospatial Leakage: Precise latitude, longitude, altitude, and direction vectors encoded in Degree-Minute-Second (DMS) rational structures, pinpointing residences, schools, and workplaces within sub-meter precision.
  • Device Fingerprinting: Camera manufacturer, hardware model, unique lens serial numbers, internal firmware versions, and exposure calibrations.
  • Temporal Auditing: Microsecond timestamps of capture and modification, enabling chronological tracking of individuals across distinct physical venues.
  • Indefinite Data Retention: Once shared across web services, recipient platforms retain cached ciphertexts indefinitely, granting unrestricted access without sender-enforced revocation or cryptographic self-destruction.
5-Line Executive Project Workflow Summary:
PrivacyLens ingests raw media, parses binary EXIF headers into an owner-restricted RSA-OAEP vault, and completely sterilizes the public raster. The clean image is subjected to a keyed 2D block spatial transposition pre-processor and encrypted via AES-256-GCM with a 128-bit GMAC authenticity tag. The 256-bit Data Encryption Key is split into two shards using 2-of-2 XOR secret sharing, isolating Shard A in client URL fragment anchors while Shard B is guarded on the server with strict TTL scheduling. Recipients recombine shards strictly in volatile browser RAM for transient viewing without hard-disk exposure. Upon expiry or burn-on-read, Shard B is zeroized to 0x00, creating an unbreakable 2^256 Shannon entropy wall, while all actions are immutably bound in a SHA-256 hash-chain audit ledger.

3.1.1 Scratch to End-to-End Step-by-Step Guide

  1. Binary Stream Ingestion: Ingest raw digital media bytes; inspect magic bytes (0xFFD8FFE1 for JPEG/EXIF) to locate binary image headers.

3.1.3 Cryptographic Engineering Explanation

Module 1 eliminates metadata surveillance while preserving non-repudiable legal ownership. When media is uploaded, the parser inspects binary tag markers. GPS coordinates are represented as triplets of rational integers: Degrees (D), Minutes (M), and Seconds (S). The system parses these fractions and computes signed decimal coordinates. To resolve the conflict between privacy sanitization and copyright proof, the module mints an RSA-2048 keypair for the user (n, e, d). The original, unsanitized EXIF dictionary is encrypted under a fresh symmetric envelope key K_env, which is subsequently encrypted using the owner's public key (e, n) using RSA-OAEP (Optimal Asymmetric Encryption Padding) with SHA-256 mask generation (MGF1). This guarantees that neither third-party recipients nor cloud servers can access the owner's camera or location history, while providing the owner with mathematical proof of original capture.

3.2 Module 2: Sensitive Metadata Removal & Classical Transposition Pre-processor

3.2.1 Scratch to End-to-End Step-by-Step Guide

  1. Raster Deconstruction: Decode image bytes into an uncompressed 2D RGB pixel matrix, discarding all non-image binary markers and headers.
  2. Keyed 2D Spatial Block Transposition: Subdivide the image raster into a grid of 16x16 pixel macro-blocks. Generate a deterministic pseudo-random permutation sequence using a seed key and shuffle block spatial coordinates.
  3. Anti-Steganography Scrubbing: Re-quantize pixel color values, normalise bit depth, and strip Least Significant Bit (LSB) planes to eliminate covert steganographic watermarks.
  4. Clean Raster Re-Encoding: Re-encode the sanitized raster into standard JPEG/PNG formats with clean, rebuilt application headers containing zero residual metadata bytes.
  5. Perceptual & Cryptographic Integrity Attestation: Compute the 64-bit Discrete Cosine Transform (DCT) Perceptual Hash (pHash) and compare the sanitized asset with the original to verify zero perceptual distortion (D_H = 0), while confirming binary cryptographic modification (SHA256_orig != SHA256_clean).

3.2.2 5 Core Points (Slide-Ready Summary)

  • Deterministic APP1 Stripping: Removes all metadata segments (EXIF, XMP, IPTC) down to the binary level with zero residual byte leakage.
  • Classical 2D Transposition Pre-processor: Integrates Unit 1 cryptographic principles by shuffling 16x16 pixel macro-blocks before modern encryption.
  • Anti-Steganographic Normalization: Sanitizes Least Significant Bit (LSB) planes to prevent covert communication channels and embedded payloads.
  • DCT Perceptual Hash (pHash) Attestation: Computes a 64-bit perceptual fingerprint to mathematically prove that visual image quality is 100% preserved.
  • Dual-Attestation Verification: Validates that while binary hashes change completely (SHA256_clean != SHA256_orig), perceptual Hamming distance equals zero (D_H = 0).

3.2.3 Cryptographic Engineering Explanation

Module 2 bridges classical cryptography (Unit 1 syllabus: Transposition Ciphers) with modern image sanitization. Standard sanitizers simply rewrite headers, often leaving orphaned metadata blocks in application segments. PrivacyLens completely decodes the image into an uncompressed spatial pixel tensor. The tensor is partitioned into macro-blocks B_(i,j) of dimension b x b pixels. A permutation mapping derived from a transposition key shuffles the spatial coordinates of each block, disrupting spatial correlation and visual recognition before reaching the modern cipher. To attest that sanitization preserves human perceptual fidelity without introducing artifacts, the module applies a 2D Discrete Cosine Transform (DCT) to an 8x8 downsampled grayscale representation, computing a 64-bit perceptual hash h_pHash. The Hamming distance D_H evaluates to 0, mathematically proving identical visual fidelity while confirming binary metadata destruction.

3.3 Module 3: Authenticated Media Encryption & Cryptographic Tamper Defense

Syllabus Unit: Unit 2 Symmetric Ciphers & AEAD Standards: NIST SP 800-38D / FIPS 197 / GF(2^128)
Figure 3.3: Module 3 AES-256-GCM Architecture & Galois Tamper Detection

3.3.1 Scratch to End-to-End Step-by-Step Guide

  1. Payload Ingestion: Ingest the sanitized raster bytes P from Module 2 into memory.
  2. CSPRNG Parameter Generation: Sample a fresh 256-bit symmetric Data Encryption Key (DEK) and a unique 96-bit Initialization Vector / Nonce (IV) using an OS cryptographically secure entropy source (os.urandom).
  3. Counter Mode Stream Encryption: Initialize the counter J_0 = IV || 0^31 1. For each 128-bit block P_i, encrypt the incremented counter under AES-256 and XOR with plaintext: C_i = P_i XOR AES_K(J_i).
  4. Galois Field GHASH Authentication: Evaluate the GHASH polynomial over the finite field GF(2^128) across authenticated associated data (AAD) and all ciphertext blocks C.
  5. GMAC Tag Creation & Tamper Lab Simulation: Encrypt the GHASH accumulator with AES_K(J_0) to form the 128-bit GMAC Tag. In the Attack Lab, intentionally mutate a single ciphertext bit (C'[i] = C[i] XOR 0x01) and verify that the decryption engine immediately triggers an InvalidTag exception, rejecting modified data with zero plaintext exposure.

3.3.2 5 Core Points (Slide-Ready Summary)

  • NIST FIPS 197 Authenticated Cipher: Employs AES-256-GCM, the gold standard for confidentiality and cryptographic authenticity in a single unified pass.
  • 96-bit Nonce Randomness: Generates unique, non-repeating initialization vectors from OS entropy pools, defeating replay attacks.
  • Counter (CTR) Mode Stream Efficiency: Enables parallelized block encryption with instantaneous sub-millisecond execution over multi-megabyte images.
  • Galois Field GF(2^128) Polynomial Tag: Generates a 128-bit GMAC authentication tag capable of detecting single-bit tampering with probability 1 - 2^-128.
  • Attack Lab Resilience: Programmatically demonstrates that bit-flip attacks, header truncation, and replay attempts result in instant execution halts.

3.3.3 Cryptographic Engineering Explanation

Module 3 implements modern Authenticated Encryption with Associated Data (AEAD) to protect media payloads from both eavesdropping and ciphertext alteration. Traditional cipher modes like CBC are susceptible to bit-flipping and padding oracle attacks. AES-GCM combines counter-mode confidentiality with Galois Message Authentication Code (GMAC) integrity. Plaintext blocks are encrypted by XORing with the AES output of an incrementing counter block. Authenticity is enforced by computing the GHASH polynomial over the field GF(2^128) defined by the irreducible polynomial f(x) = x^128 + x^7 + x^2 + x + 1. The hash key H = AES_K(0^128) is multiplied against each block in GF(2^128). The final authentication tag is computed as Tag = GHASH_H(AAD || C) XOR AES_K(J_0). If an adversary modifies even a single bit of stored ciphertext C, the recomputed tag will diverge from Tag with certainty 1 - 2^-128, completely preventing unauthorized modification.

3.4 Module 4: 2-of-2 Ephemeral Key Sharding & Cryptographic Self-Destruction

Syllabus Unit: Unit 2 & 4 Secret Sharing & Forward Secrecy Standards: Shannon Information Theory / Secure RAM Scrubbing
Figure 3.4: Module 4 2-of-2 Ephemeral Secret Sharding & Entropy Wall

3.4.1 Scratch to End-to-End Step-by-Step Guide

  1. Secret Key Decomposition: Take the 256-bit symmetric DEK from Module 3. Sample a random 256-bit vector from the CSPRNG entropy pool to create Shard A: K_token from {0,1}^256.
  2. XOR Shard Derivation: Derive Shard B via bitwise XOR: K_server = DEK XOR K_token.
  3. Client URL Fragment Binding: Embed Shard A strictly within the URL fragment anchor (e.g., /view/<uuid>#key=ShardA). Web browsers RFC-mandate that fragment identifiers are never transmitted to web servers in HTTP request headers.
  4. Server Storage with Strict TTL: Store Shard B in the server database accompanied by a strict expiration timestamp (Time-To-Live countdown: 60s, 300s, 86400s).
  5. Volatile RAM Recombination & Burning: When an authorized recipient opens the link, the browser reads Shard A from the URL fragment and fetches Shard B from the server. Recombination DEK = K_token XOR K_server occurs strictly in volatile RAM to decrypt the image onto an HTML5 Canvas blob. Upon reading or TTL expiry, Shard B is overwritten in server memory with 0x00 null bytes (memory zeroization), permanently rendering the ciphertext unrecoverable.

3.4.2 5 Core Points (Slide-Ready Summary)

  • Information-Theoretic Secret Sharding: Splits the 256-bit DEK into two independent shards using 2-of-2 bitwise XOR operations.
  • Client-Side Anchor Isolation: Employs URL fragment identifiers (#key=...) so that the web server remains blind to Shard A.
  • Volatile In-Memory Decryption: Reconstructs keys strictly inside volatile RAM; decrypted rasters are streamed directly to HTML5 canvas memory without writing a single byte to the hard drive.
  • Automated Memory Zeroization: Implements cryptographic shredding where Shard B is aggressively overwritten with 0x00 null bytes upon access or TTL expiry.
  • Claude Shannon Entropy Wall: Post-zeroization, possessing Shard A leaves exactly 256 bits of unknown entropy (2^256 keyspace), guaranteeing perfect forward secrecy.

3.4.3 Cryptographic Engineering Explanation

Module 4 enforces temporal access control and irreversible self-destruction without relying on unreliable third-party deletion requests. Based on Claude Shannon’s 1949 theorem of Perfect Secrecy, a one-time pad key K_server derived via K_server = DEK XOR K_token exhibits complete statistical independence from the secret DEK whenever K_token is uniformly distributed over {0,1}^256. The conditional entropy satisfies H(DEK | K_token) = H(DEK) = 256 bits. The server never observes Shard A because it resides in the URL hash component, which RFC 3986 specifies is parsed exclusively on the client. When access criteria expire or burn-on-read is triggered, the server zeroes the memory holding Shard B. Without Shard B, reconstructing the original image requires evaluating 2^256 combinations—an astronomical computational complexity that remains insurmountable against any classical or quantum adversary.

3.5 Module 5: Tamper-Evident SHA-256 Hash-Chain Audit Ledger & Dashboard

Syllabus Unit: Unit 3 Cryptographic Hash Functions & MAC Standards: FIPS 180-4 / Merkle-Damgard Structural Integrity
Figure 3.5: Module 5 SHA-256 Hash-Chain Audit Ledger Architecture & Traversal

3.5.1 Scratch to End-to-End Step-by-Step Guide

  1. Genesis Block Seeding: Mint an immutable Genesis Block (Block_0) with a hardcoded previous hash H_0 = 0000...0000 and event type LEDGER_GENESIS_INIT.
  2. Sequential Security Event Ingestion: As the system executes (metadata profiling, sanitization, encryption, viewing, and zeroization), generate an event tuple containing block index i, timestamp T_i, event type E_i, and payload data D_i.
  3. Merkle-Damgard Chained Hashing: Read the previous block’s hash H_(i-1) and compute the current block hash: H_i = SHA-256(i || H_(i-1) || E_i || D_i || T_i). Commit the record to the immutable database ledger.
  4. Ledger Traversal Algorithm: When the administrative dashboard or verification auditor inspects the system, execute a linear traversal from Block_0 to Block_N. Recompute every block’s SHA-256 digest and verify that Block_i.prev_hash == Block_(i-1).block_hash.
  5. Intrusion Pinpointing: If a rogue database administrator or malicious actor alters an event record in SQLite, the traversal algorithm immediately detects digest divergence and pinpoints the exact block index of unauthorized tampering.

3.5.2 5 Core Points (Slide-Ready Summary)

  • Immutable Hash-Chained Audit Trail: Cryptographically binds every lifecycle event into an append-only ledger using SHA-256 Merkle-Damgard chaining.
  • Genesis Anchor Security: Anchors the cryptographic chain to a deterministic Genesis block, preventing historical ledger truncation.
  • Mathematical Forward Linkage: Every block digest incorporates the previous block's 256-bit hash, rendering retroactive tampering mathematically detectable.
  • Automated Traversal Verification: Features a built-in verification engine that re-computes every chained digest across the entire ledger history.
  • Precise Intrusion Localization: Instantly pinpoints the exact block index where data corruption, deletion, or unauthorized modification occurred.

3.5.3 Cryptographic Engineering Explanation

Module 5 provides non-repudiation and tamper evidence for all media operations without requiring external third-party blockchain networks. Employing the FIPS 180-4 Secure Hash Algorithm 256-bit (SHA-256), the audit ledger forms a Merkle-Damgard chain where each block B_i encapsulates (i, H_(i-1), E_i, D_i, T_i) and produces H_i = h(i || H_(i-1) || E_i || D_i || T_i). Due to the collision resistance and avalanche effect of SHA-256, changing a single bit in the event description of Block_k will alter H_k, which causes a mismatch at Block_(k+1).prev_hash. Recomputing the chain will produce completely different hash values for all subsequent blocks k+1, ..., N. This mathematical property enables the audit dashboard to prove whether the ledger remains in an uncompromised, pristine state or identify the exact moment an unauthorized modification was attempted.

4.2 In-Depth Technical Justification of Novelties

Existing privacy tools and commercial cloud services exhibit fundamental security flaws:

PrivacyLens resolves this through Asymmetric Provenance Envelope Vaulting: metadata is preserved, encrypted with the owner’s RSA public key, and bound to the asset without leaking location to recipients.
  • The Indefinite Access Problem: Standard cloud platforms (Google Drive, Dropbox, WhatsApp) provide static access links. Even if an image is "deleted", cached ciphertexts and decryption keys persist on corporate servers. PrivacyLens enforces true ephemeral sharing: because the server only holds Shard B, wiping Shard B renders the remote ciphertext mathematically indistinguishable from random noise (H = 256 bits of entropy).
  • Client Blindness: By exploiting RFC 3986 URL hash mechanics, PrivacyLens ensures that Shard A is never included in the HTTP request payload received by the server. The server operates in a zero-knowledge state regarding Shard A.
